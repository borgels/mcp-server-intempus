# Intempus API notes

Verified against a production Intempus account on 2026-09-29, with read-only GETs and a live write test on a throwaway test employee. Also based on the OpenAPI 2.0 spec at `https://intempus.dk/web-doc/v1/specs/swagger.json` (195 paths). Anything marked **unverified** comes from the spec only.

## Transport

- Base URL `https://intempus.dk/web/v1/`, Django + tastypie, JSON only.
- `Authorization: ApiKey <username>:<key>`. The username is case-sensitive: the right casing gives 200 with `x-django-user` / `x-django-role` response headers (the key in use has role `admin`), the wrong casing gives 401 with `WWW-Authenticate: CustomBasic realm="django-tastypie"`.
- The key is bound to an Intempus user. There is no impersonation header; a work report is created for another employee by setting its `employee` URI.
- Relations are resource URIs (`/web/v1/employee/12/`); nested objects are accepted too.
- Rate limit: 500 requests/min and 50,000/day per user; 429 with `Retry-After`.
- Pagination: `limit` (default 1000, max 10000). Offset paging is deprecated; cursor paging uses `pagination_type=cursor&after=…` and `meta.next`. **`explored_employee_balance` and `schedule` return HTTP 500 with `pagination_type=cursor`.**
- Filters: `field`, `field__in` (comma-separated), `__gte/__lte/__gt/__lt`, `__icontains` where allowed. A filter that is not allowed returns 400, e.g. `{"error": "The 'email' field does not allow filtering."}` and `{"error": "'iexact' is not an allowed filter on the 'username' field."}`.
- Errors: `{"error": "…"}`, `{"error": ["…"]}` (Danish messages), `{"error_message": "…"}` on 500s, and field errors keyed by resource. A missing detail returns 404 with an empty body.
- `creation_id` on create makes retries idempotent.
- Incremental sync via `logical_timestamp__gt` and the `Logical-Timestamp` header. Deletions are not reported.

## Account-specific findings that shape the design

- The Intempus `email` is often a private address, so self-service needs the Intempus username or work email set to the Entra UPN, or an `INTEMPUS_IDENTITY_MAP` entry.
- Approver levels (`responsible`) can exist without any `responsible_for_*` assignments. The approver endpoint then shows nobody until assignments are made, or `INTEMPUS_APPROVER_UNASSIGNED_SCOPE=all` is set.
- Some work models have no work types, so employees on them cannot register time at all.
- `employee.contract` embeds full contract objects (`start_date`, `end_date`, `locked_date`, `work_model`, `work_model_name`).

## Work reports and approval

- Required on create: `company`, `employee`, `amount`. `amount` is a decimal string (`"2.53333…"`). Times are `HH:MM:SS`; `start_week_number` is derived.
- `approved` (bool) is read-only in the spec (not in the patch schema) and follows the final approval.
- `approved_by` is a list with one entry per level: `{level: "second_approver", label: "Anden godkender", date, time, name, number, username}`. `date` is `null` while that level is pending. The final approver's approvals in the data carry `date` and `username`.
- **Approval is not possible through the API** (live test):
  - `PATCH {approved: true}` is silently ignored.
  - `approved_by_initial` / `approved_by_final` expect a **userprofile** URI. An employee URI gives 404 "An incorrect URL was provided … for the 'UserProfileResource' resource".
  - Setting both, with the approver holding `final_approver` and assigned to the employee via `responsible_for_employee`, still leaves `approved=false`, also after 8 seconds.
  - Reports approved in the UI have `approved_by_final: null`. The approval lives elsewhere, and `historical_work_report` has no approval fields.
- Locking with `POST work_report/bulk/ {ids, origin, immutable, action: "work_report_state"}` needs `origin` (400 `'origin'` without it). Even then it gives 401 "Work report state can only be updated if the feature is enabled", so the feature is off on ONE's account.
- The period lock works: PATCH `contract.locked_date`, verified. Registering inside the locked period is refused.
- Validation errors seen:
  - "Start- og sluttid skal være angivet for denne arbejdstype" (a work type with `report_interval`)
  - "Projektarbejde skal være tilknyttet et projekt" (the category is `case_related`)
  - "Kontrakt (…) og arbejdstype (…) skal tilhøre samme arbejdsmodel"
- `creation_id`: a create repeated with the same value returns the same report (verified).
- Observed `origin` values: `intempus:mobile`, `intempus:economic_workreport_sync`, `intempus:overtime`. Overtime lines ("Overarbejde 1.-3. time (automatisk)") are generated by Intempus.

## Balances

- `balance`: definitions with `name`, `unit` (Dage/Timer/km), `recurring_mode`, `visible` (to employees), `visible_for_admins_and_approvers`, `start_date`.
- `explored_employee_balance`: filters `employee_pk`, `employee_pk__in`, `balance_pk`, `start_date`, `end_date` (both needed). It returns `positive_sum`, `negative_sum`, `advance_spent`, `advance_remaining` per balance with movement in the window.
- Accrual is dated at month end. For one employee, `end_date=2026-09-29` returned nothing, `2026-09-30` returned 2.08 days, `2026-12-31` returned 8.32, and `2027-08-31` returned 25.0 (the full holiday year).

## Employees (admin)

- `employee` POST needs `company`, `password`, `name` and `username`. `number` must be a positive integer below 1,000,000.
- `password_generation` must be sent. `0`, which is also the default, is "only valid for existing users". `1` means Intempus generates a password and emails it, and needs `email`. `2` means use the given password.
- Every new employee gets a `userprofile` automatically. `DELETE employee` then gives 409 "Kan ikke slette Medarbejder da Brugerprofiler er relateret og bør slettes først", and `userprofile` has no DELETE (405). **Employees cannot be deleted through the API.**
- Detail responses may embed relations as objects: `work_type/{id}/` returns `work_model` and `work_category` as full objects, while lists return URIs.
- `userprofile` holds `may_log_into_backend` / `may_log_into_approval` and filters only on `id__in`.
- Required on `contract` POST: `employee`, `work_model`, `start_date`.
- Responsibility: `responsible {employee, level}`; `responsible_for_employee {employee, responsible}` (and the same for `department`, `case`).
- Offboarding (verified): PATCH `contract.end_date` works, and so does PATCH of the userprofile login flags. PATCH `employee.unsubscribe_date` is ignored.
